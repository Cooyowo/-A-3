## 1. 身份与明牌

**本节文档已明确、无需 DEFAULT**：明牌只有双地者可用（§2.5）；明牌者必然是地主方 L（双地必持 ♠3+♠A）；时机在「发完牌之后、供牌之前」；只公开 ♠3/♠A 两张；取消本局供牌且赢方不回牌；明牌不可反悔；明牌者首发；本局结果供牌张数翻倍 6→12。

**Q-001｜明牌决策的超时时长**
- 来源：《玩法说明》§2.5、§5.1；《开发文档》§7.2
- 问题：玩法说明只写「发完牌之后、供牌之前」可明牌，没给超时值；开发文档写「超时默认不明牌，10s」，但这个 10s 是唯一依据。
- 默认实现：联机模式给双地者 10s 决策窗口；服务端计时，到点未提交 `REVEAL` 即视为「不明牌」，直接进入供牌阶段。
- 影响：REVEAL 阶段的退出条件、服务端计时器、客户端倒计时。写错会导致阶段卡死，或被误判成明牌。
- 需用户拍板：是

**Q-002｜热座（M2 单机）是否启用倒计时**
- 来源：《开发文档》§7.2、§14.5（可配置项：锁定窗口时长、明牌/回牌超时）
- 问题：文档只给了联机式超时默认值，没说本地热座（同一浏览器切四个人）是否也自动超时。
- 默认实现：热座/单机**禁用所有倒计时**，明牌、锁定窗口、回牌、挑回牌一律等玩家点击推进；倒计时仅在 M3 联机时启用。M2 用同一套状态机，只把 timer 换成「手动推进」。
- 影响：M2 热座体验、状态机推进方式（自动 vs 手动）、M2/M3 代码分支。写错会出现「热座里还没点就被自动抽走」。
- 需用户拍板：是

**Q-003｜明牌是否需要二次确认**
- 来源：《玩法说明》§2.5（明牌不可反悔）
- 问题：规则只说不可反悔，没说误触了怎么办；但明牌是不可逆的大动作（作废供牌 + 翻倍）。
- 默认实现：点「明牌」弹二次确认（写明「本局取消供牌、由你首发、本局供牌翻倍且不可撤销」）；确认后服务端立即锁死，断线重连也不能撤销。
- 影响：UI 交互、服务端幂等（重复 `REVEAL` 必须拒绝）。写错会出现「误点直接翻倍」。
- 需用户拍板：否

**Q-004｜没有供牌债务的局，能否明牌**
- 来源：《玩法说明》§2.5（未限制）；《开发文档》§12 边界 #22（可以）
- 问题：双地者在本局没有上一局债务时（首局、上一局平局、上一局已明牌作废后），是否仍可选择明牌。
- 默认实现：**允许**。无债务时明牌的效果是：公开 ♠3/♠A、由明牌者首发（压过 ♦4 首发权）、本局若产生供牌则翻倍。开发文档边界 #22 已如此约定。
- 影响：引擎 `canReveal`、首发权解析、UI 按钮显示条件。写错会让玩家白丢一次翻倍机会，或反之被禁止使用规则赋予的权利。
- 需用户拍板：是

**Q-005｜明牌作废的供牌范围：整局，还是只作废明牌者自己的债务**
- 来源：《玩法说明》§2.5、§7.2；《开发文档》§9.1（`pendingDebt = null`）
- 问题：规则写「取消本局应执行的供牌（上一局的供牌债务直接作废，赢方也不用回牌）」，但没强调「其他输家的债务也一起作废」。极端情形：上一局双地明牌 L 赢 → 3 个 F 各欠 4 张；下一局其中一个 F 成了双地者（此时他是 L）并明牌 → 整笔 12 张债务（含另外两个 F 的 8 张）全部作废。
- 默认实现：**整局作废**：`pendingDebt = null`，本局不供牌、不回牌，其他输家也免供；UI 明确提示「明牌取消本局全部供牌」。
- 影响：供牌状态机、结算、多人债务场景。写错会出现「只作废本人份额」的私改规则。
- 需用户拍板：是

**Q-006｜「本局债务作废」与「本局翻倍」并存 → 12 张债务可被反复作废**
- 来源：《玩法说明》§2.5、§7.8、§9.9；《开发文档》§9.1
- 问题：两份文档都同时要求「明牌作废本局债务」和「本局输赢供牌翻倍」。推论：上一局明牌输 → 欠 12 张；本局又是双地 → 明牌 → 12 张作废；本局再输 → 下一局又欠 12 张。理论上可无限循环，债务永远不落地（每次都需要再赌一次「双地」这个极小概率事件，且每次明牌都在提高下一局的风险）。
- 默认实现：按文档执行（作废 + 翻倍各自生效），不做额外限制；服务端事件日志里同时记录 `debtVoided` 与 `nextDebtDoubled`，便于复盘；M1 测试里补一个「连续两次双地明牌」的用例确认没有死循环。
- 影响：结算 / 供牌 / 风险平衡。写错可能出现「债务永不执行」或「重复扣债」。
- 需用户拍板：是

**Q-007｜明牌后的公开范围与 UI 标注**
- 来源：《玩法说明》§2.5、§7.6
- 问题：规则说只公开 ♠3/♠A 两张，但一旦公开，场上身份其实已完全确定（明牌者 = 唯一 L，其余三人全是 F）。
- 默认实现：只广播 ♠3、♠A 两个 `cardId`；客户端据此把其余三家标为「非地主方（F）」——这是从公开信息推导，不算泄露隐藏信息。明牌者的其余 11 张不公开。
- 影响：UI 身份标识、隐藏信息校验（M3 抓包不应出现第 3 张牌）。
- 需用户拍板：否

**Q-008｜12 张供不出时，明牌询问要不要合并**
- 来源：《玩法说明》§7.8、§9.9；《开发文档》§7.2（REVEAL 先问）、§8.2（SUPPLY CHECK 再问）
- 问题：按开发文档的顺序，双地者会先被问一次「是否明牌」；若答否，又在 CHECK 阶段因为「11 张 < 12 张」被问一次「明牌 or 重新发牌」。同一件事问两次。
- 默认实现：**合并为一次决策**。发牌后若判定「本局 CHECK 必定失败」（即他同时是双地者且债务需要 12 张），REVEAL 阶段直接弹「明牌（债务作废）/ 重新发牌（债务保留）」；否则仍只问「是否明牌」。判定条件：`doubleSeat === debtLoser && amountPerLoser > 11`。
- 影响：REVEAL/SUPPLY 阶段的人机流程、UI 弹窗数量、M1 状态机分支。不合并会让玩家困惑「我不是刚拒绝过明牌吗」。
- 需用户拍板：是

**Q-009｜明牌后供牌阶段完全跳过时的过场**
- 来源：《玩法说明》§2.5、§7.2；《开发文档》§7.3（`revealedSeat != null → LOCK_WINDOW`）
- 问题：明牌后本局无任何供牌/回牌，UI 是否还需要「供牌阶段」这屏。
- 默认实现：跳过 SUPPLY，直接进锁定窗口；中间插一条 1.0s 的提示「明牌：本局供牌已取消」，不阻塞状态机。
- 影响：UI 流程、观感。写错会让玩家以为漏了供牌步骤。
- 需用户拍板：否

**Q-010｜明牌者能不能提前锁定第三名**
- 来源：《玩法说明》§2.5、§8.1；《开发文档》§9.2
- 问题：规则说「地主方永远不可能提前锁定」（§8.1），明牌者必为 L，所以逻辑上不可能。但实现时容易漏判。
- 默认实现：锁定资格判定与 L/F 身份无关，只看「手牌 13 张是否全部 ≤10」；明牌者手牌必含 ♠3、♠A（rank 16/14 > 10），天然不合格。加一条断言：`revealedSeat` 的玩家不得出现在锁定申请列表。
- 影响：引擎锁定资格、UI 按钮可见性。写错会出现「双地者锁定第 3 名」的荒谬局面。
- 需用户拍板：否

## 2. 首发权

**本节文档已明确、无需 DEFAULT**：首发优先级 = 明牌者 > 上交最大牌者 > ♦4 持有者（§5.2）；首局由 ♦4 持有者首发；平局后由 ♦4 持有者首发；明牌取消供牌后由明牌者首发；供牌后由「上交的牌最大的玩家」首发（§7.7）。

**Q-011｜供牌池最大牌并列时，谁首发（并列 tie-break）**
- 来源：《玩法说明》§1.4、§1.5、§7.3、§7.7；《开发文档》§8.6
- 问题：规则规定 4~10 同点数「一样大」。若两个输家各自上交的最大牌都是 9（如 ♠9 与 ♥9），按规则它们一样大，无法选出唯一的「最大牌持有者」。同理，回牌挑选顺序（§7.5）也会并列。开发文档用 `cmpCard` 的 `id` 兜底，但 `id` 是发牌实现细节（0..51 的构造顺序），对玩家无意义、且换洗牌实现就变。
- ~~默认实现~~ **用户确认（2026-11-15）**：并列时**按花色比大小**（♠ > ♥ > ♣ > ♦）。一副牌里不会出现两张完全相同的牌，所以点数相同必然能靠花色分出先后，实际不存在真并列；若实现中出现完全并列（理论不可能），按座位号升序兜底。
- 落地要求：`cmpCard` 在点数相同时统一比花色（4~10 也比，仅用于确定先后，不影响「取最大的 N 张」结果）；首发权与回牌挑选顺序共用同一个比较函数。
- 影响：引擎首发解析、回牌顺序、测试确定性。写错会导致同一副牌不同实现下首发出入、回放对不上。
- 状态：`CONFIRMED`（已同步改《玩法说明》§7.5 / §7.7 / §10、`《开发文档》§2.1`；代码与测试在 M1 落地）
- 需用户拍板：否（已确认）

**Q-012｜明牌者同时是「上交最大牌者」怎么判**
- 来源：《玩法说明》§5.2 补充说明、§7.7；《开发文档》§8.6
- 问题：两条优先级看起来会冲突。
- 默认实现：**不可达**——明牌会作废整局供牌，本轮根本不存在「上交最大牌的人」。实现上 `resolveFirstSeat` 用短路优先级（明牌者 → 供最大牌者 → ♦4），不做冲突检测，并加断言「明牌者的局 `firstSeatBySupply === null`」。
- 影响：状态机不变量、断言。写错会写出互相覆盖的首发赋值。
- 需用户拍板：否

**Q-013｜有待执行债务、但供牌池为空**
- 来源：《玩法说明》§6.2、§7.2；《开发文档》§8.2、§8.3
- 问题：是否存在「有债务但没人交牌」的合法局面（例如债务记录存在、输家 0 人）？
- 默认实现：**不可达**。结算表里债务总额 ∈ {2,4,6,12}，输家数 ∈ {1,2,3}，`amountPerLoser ≥ 1`，且 CHECK 保证每人可供张数够。若真出现，按「不变量破坏」处理：跳过供牌、记录 `ENGINE_INVARIANT_VIOLATION`、首发回退到 ♦4 持有者，M1 测试不允许出现。
- 影响：状态机防御分支、错误日志。写错会把 bug 掩盖成「正常平局」。
- 需用户拍板：否

**Q-014｜♦4 持有者按哪个时点取算**
- 来源：《玩法说明》§5.2、§7.7；《开发文档》§8.6
- 问题：♦4 **可以被回牌转移**（赢家自选回牌时可以把 ♦4 还出去，超时自动还最小牌时几乎必然还 ♦4）。所以「♦4 持有者」在供牌前和供牌后可能不是同一个人。
- 默认实现：一律在**本局供牌/回牌全部结束后、锁定窗口开始前**解析首发权，取当时的 ♦4 持有者；本局内不再重算。首局与平局局没有供牌，口径相同（相当于「上一局结束时的持有者」）。
- 影响：引擎 `resolveFirstSeat`、UI 首发提示。写错会出现「首发说 A，实际 B 出牌」。
- 需用户拍板：否

**Q-015｜首发者本局锁定成功（拿到第 3 名）后，谁先出牌**
- 来源：《玩法说明》§8.2、§8.4；《开发文档》§9.2
- 问题：首发权在锁定窗口之前就解析完了，但满足锁定条件的人正是 F（可能是「供最大牌者」或「♦4 持有者」）。他一旦锁定成功就退出本局，原定首发失效，规则没写由谁接。
- 默认实现：**从锁定者的下家起、按逆时针找第一个仍在场的玩家首发**（等价于「原首发顺延一位」）；并在事件 `LOCKED` 广播后补发 `FIRST_SEAT_CHANGED`。若同时有多人锁定则全部失败，首发不变。
- 影响：出牌阶段起点、UI 提示、M1「锁定+首发」测试。不处理会直接卡在出牌阶段（currentSeat 指向已退出玩家）。
- 需用户拍板：是

**Q-016｜双地者未明牌时是否仍有首发权**
- 来源：《玩法说明》§5.2、§7.7
- 问题：双地者拒绝明牌后，是否因为是「双地」而被排除在「供最大牌者首发」之外。
- 默认实现：**不排除**。若他是上交最大牌者，则他首发；若他没供牌（例如他不需要供牌而别人供了），则按供最大牌者；都没有则 ♦4 持有者。双地身份本身不改变首发规则。
- 影响：引擎首发解析、玩家预期。写错会让双地者被莫名剥夺首发。
- 需用户拍板：否

**Q-017｜首发权何时解析、何时公示**
- 来源：《玩法说明》§5.2、§8.4；《开发文档》§7.3、§8.6
- 问题：首发要等供牌结束才能定，但锁定窗口有 5s，期间玩家要不要知道首发是谁？
- 默认实现：供牌结束后立即解析并广播 `FIRST_SEAT_RESOLVED`（含首发座位与理由），锁定窗口里 UI 显示「本局首发：X」。若因锁定导致变更（Q-015），再广播一次变更事件。
- 影响：UI 信息展示、事件流契约。写错会让玩家在锁定窗口里看不到关键决策信息。
- 需用户拍板：否

**Q-018｜重新发牌（REDEAL）后首发权怎么算**
- 来源：《玩法说明》§7.8；《开发文档》§7.1、§8.6
- 问题：重发会换掉全部手牌，原首发解析结果作废。
- 默认实现：REDEAL 回到 DEAL，清空 `firstSeat/firstSeatBySupply/revealedSeat`；等重新发牌 + 供牌（债务仍在）完成后再统一解析首发。重发次数不影响首发规则。
- 影响：状态机、重发流程。写错会沿用旧首发，出现「首发在重发前就被写死」。
- 需用户拍板：否

**Q-019｜「上交的牌最大」的比较口径**
- 来源：《玩法说明》§7.7；《开发文档》§8.6
- 问题：是拿「每个输家上交牌里的最大牌」互相比，还是拿「供牌池排序后的第一张」？两者通常等价，但实现路径不同；另外双地 L 输时只有 1 个输家。
- 默认实现：用 `perLoser` 里每个输家的最大牌比较（不走全局池），并列用 Q-011 的座位号规则；只有一个输家时他必然首发（双地 L 输 6/12 张的场景）。
- 影响：引擎首发解析、测试用例。写错在「多输家 + 并列」时结果不稳。
- 需用户拍板：否

## 3. 出牌流程

**本节文档已明确、无需 DEFAULT**：「不要」只表示这一圈不出、不锁死后续（§5.5）；出完最后一张本墩立即结束、由在场下家领出（§5.6、边界 #20）；三条夹一可压三条、三条不能压三条夹一（§5.7.2）；三条阶段一旦结束本局不再出现三条/三条夹一（§5.7.6）；炸弹不能压单张/对子（§4.1、边界 #8）；领出者打出非三条牌型即结束三条阶段（§5.7.5，实现冲突见 Q-023/Q-024）。

**Q-020｜「在场玩家」的定义**
- 来源：《玩法说明》§5.4、§5.6、§8.4；《开发文档》§7.4、§12 边界 #17
- 问题：一墩结束时「其余所有仍在场玩家都不要」里的「在场」，是否包含已出完者和已锁定者。
- 默认实现：**在场 = `!player.out`**（`out` 在出完与锁定成功时都会置 true）。轮转 `nextActiveSeat`、墩结束计数、结束判定、UI 轮转高亮全部用同一个谓词，不允许用「手牌数 > 0」代替。
- 影响：引擎轮转/墩结束判定、UI。写错会出现「等已出完的人表态」而卡死。
- 需用户拍板：否

**Q-021｜一墩结束的门限怎么算**
- 来源：《玩法说明》§5.4、§5.5；《开发文档》§7.4（`passesSinceLastPlay >= activeSeatCount - 1`）
- 问题：`activeSeatCount - 1` 是「在场人数减一」，隐含「最后出牌者一定还在场」这个假设；一旦这个假设破了，门限就会算错（多要求/少要求一次 PASS）。
- 默认实现：不用减法推算，显式算 `otherActiveCount(state) = 在场人数 -（topSeat 是否在场 ? 1 : 0）`，门限 = `passesSinceLastPlay >= otherActiveCount`；`topSeat` 为空时该墩视为自由领出，不计数。PASS 计数在每次 PLAY 时清零、每次成功领出/顺风换人时清零。
- 影响：引擎墩结束判定、自对弈死锁率。写错会频繁死锁或提前结束墩。
- 需用户拍板：否

**Q-022｜领出者能否 PASS**
- 来源：《玩法说明》§5.3、§5.6；《开发文档》§6.1（领出动作枚举未提 PASS）
- 问题：文档没说领出（`topPattern === null`）时能不能「不要」。若能，一墩永远结束不了，且「本局第一手由首发打出」也会被绕过。
- 默认实现：**领出者必须出牌，PASS 不是合法动作**，服务端 `legalActions` 不含 PASS，客户端上报 PASS 判非法。
- 影响：引擎合法动作、墩结束计数、自对弈。写错会出现死循环 / 三条阶段被绕过。
- 需用户拍板：否

**Q-023｜三条阶段内领出者「主动断掉」怎么实现**
- 来源：《玩法说明》§5.7.4、§5.7.5；《开发文档》§7.4（`startTrick(keepTop = state.threePhase)`）、§5.2（`canFollow`）
- 问题：规则说「阶段内其余人都不要 → 最后出牌者继续领出，可以继续出更大的三条/三条夹一」，同时「领出者也可以主动断掉：改打单张、对子、顺子等其它牌型」。开发文档的做法是「三条阶段保留 `topPattern` 作为基准」，但这样一来领出者的合法动作只剩「能压过基准的牌组」，单张/对子/顺子会被 `canFollow` 直接判非法——「主动断掉」不可实现。
- 默认实现：三条阶段内，领出者的合法动作 = `{能压过基准的三条/三条夹一}` ∪ `{任意合法牌型}`；打出前者则阶段继续，打出后者则阶段**立即结束**（`threePhase = false` 且后续不可复活）。跟牌玩家仍只允许「压过基准」，不允许降维。
- 影响：引擎 `legalActions` / `canPlayTripleLike` / `canFollow`、三条阶段测试 F-05/F-06/F-29。写错会让整个三条阶段玩法失真（要么锁死只能出三条，要么阶段无法结束）。
- 需用户拍板：是

**Q-024｜出现「顺风」后，三条阶段和基准牌还保留吗**
- 来源：《玩法说明》§5.6、§5.7；《开发文档》§7.4（顺风分支只清 `topPattern`，未动 `threePhase`）
- 问题：顺风（某人出完最后一张）是 §5.7.6 没列出的第三条阶段终结点。开发文档的实现会留下 `threePhase = true` 但 `topPattern = null`，于是新领出者可以打**比基准更小**的三条/三条夹一，违反 §5.7.1「必须比当前牌大」。
- ~~默认实现~~ **用户确认（2026-11-15）**：**顺风不保留三条阶段**。有人打完最后一张牌后，三条阶段立即结束，新领出者**不能**再出三条/三条夹一，只能出其它牌型；手上恰好只剩三四张时仍可用「结束牌」走完。
- 落地要求：`onPlay` 顺风分支置 `threePhase = false`（`topPattern` 同时清空）；自对弈不变量加一条「顺风后本局不再出现三条/三条夹一（结束牌除外）」。
- 影响：引擎顺风分支、三条阶段判定、自对弈不变量。写错会出现「顺风后还能接三条」。
- 状态：`CONFIRMED`（已同步改《玩法说明》§5.6 / §5.7 / §10 / §12、`《开发文档》§7.4 / §12`；代码与测试在 M1 落地）
- 需用户拍板：否（已确认）

**Q-025｜顺风后由谁领出**
- 来源：《玩法说明》§5.6、§8.4
- 问题：「他还在场的下家」具体怎么找；若下家也刚出完/已锁定怎么办。
- 默认实现：从出完者的座位按逆时针找第一个 `!out` 的玩家；若一直找不到（理论上不可能，因为此时已满足结束条件），直接进 SETTLE 并记 `ENGINE_INVARIANT_VIOLATION`。出完者本人不再获得任何回合。
- 影响：引擎轮转、结束判定。写错会死锁或让出完者继续出牌。
- 需用户拍板：否

**Q-026｜三条阶段是否必须「首发本人」的第一手开启**
- 来源：《玩法说明》§5.7 进入条件；《开发文档》§5.4（`isFirstPlay && isLeading`）
- 问题：开发文档只判断「本局还没人出过牌 + 当前是领出」，没校验出牌者是不是首发座位。正常情况下等价，但若出现「首发 PASS」或状态重入，可能被非首发玩家开启三条阶段。
- 默认实现：进入条件加一条：`state.currentSeat === state.firstSeat`。因为领出不可 PASS（Q-022），正常情况下必然成立，此判断作为防御性断言。
- 影响：引擎 `canPlayTripleLike`、状态机不变量。写错会让「本局第一手」语义漂移。
- 需用户拍板：否

**Q-027｜结束牌是「必须一手走完」还是「可以不打」**
- 来源：《玩法说明》§3.5 第 3 条；《开发文档》§5.4
- 问题：手上恰好剩 3 张同样的牌时，是否强制以三条走完；能否拆成单张/对子出。
- 默认实现：**完全可选**。结束牌只是「允许」，不强制；玩家可以从剩余 4 张里先出对子等任意合法组合，不要求一手走完。只有他自己选择打出完整的三条/三条夹一才构成结束牌。
- 影响：引擎合法动作枚举、UI 提示。写错会替玩家做决定。
- 需用户拍板：否

**Q-028｜结束牌的判定口径**
- 来源：《玩法说明》§3.5 第 3 条；《开发文档》§5.4（`hand.length === p.cards.length`）
- 问题：用「出牌前手牌张数恰好等于牌型张数」，还是「出这张后手上刚好没牌」。两者在正常出牌下等价，但和上面 Q-027 的可选性一起容易写错。
- 默认实现：出牌前 `hand.length === p.cards.length`，且必须是领出（`isLeading`），且不能在三条阶段被压制的场景下绕过基准（见 Q-024）。跟牌时永远不允许把三条/三条夹一当结束牌（跟牌必须同大类，且若在三条阶段内仍按 Q-023）。
- 影响：引擎合法性、边界测试 F-08/F-09。写错会出现「手上有 5 张却用最后 3 张走完」。
- 需用户拍板：否

**Q-029｜三条阶段能否被「重新打开」**
- 来源：《玩法说明》§5.7.6；《开发文档》§7.4
- 问题：阶段结束后，若后续又出现三条/三条夹一（例如结束牌），是否会把 `threePhase` 重新置 true。
- 默认实现：`threePhase` 只有本局第一手能置 true；任何一次关闭后本局永久 false（结束牌只是「允许出」，不重开阶段）。
- 影响：引擎状态字段、测试。写错会出现「中局突然又能出三条」。
- 需用户拍板：否

**Q-030｜锁定者在出牌阶段的处理**
- 来源：《玩法说明》§8.4；《开发文档》§12 边界 #17
- 问题：锁定者是 `out = true`，但手牌仍在（13 张）。
- 默认实现：轮转完全跳过、不参与墩内统计、不能被供牌/回牌、牌面保持公开显示在桌面一角；`legalActions` 对他返回空数组。
- 影响：引擎轮转、UI 布局、隐藏信息。写错会让已锁定玩家还能出牌。
- 需用户拍板：否

**Q-031｜出完者的最后一手是否保留为 `topPattern`**
- 来源：《玩法说明》§5.6、§5.7；《开发文档》§7.4
- 问题：顺风时开发文档清空了 `topPattern`，但三条阶段需要基准牌（Q-024），展示层也需要「本墩最后一手」。
- 默认实现：区分两个字段——`topPattern`（判定用，顺风后按 Q-024 处理）与 `lastPlayedPattern`（展示/回放用，永远保留到下一手）。避免用同一个字段同时承担两种语义。
- 影响：引擎状态设计、UI 牌桌区。写错会让展示和判定互相污染。
- 需用户拍板：否

**Q-032｜一墩结束时的状态清理**
- 来源：《玩法说明》§5.4；《开发文档》§7.4（`startTrick`）
- 问题：哪些字段在换墩时清、哪些留。
- 默认实现：`passesSinceLastPlay = 0`；`topPattern = 三条阶段 ? 基准 : null`；`topSeat` 保留到下一手出牌（供 UI 显示墩赢家）；`currentSeat = 领出者`；`isFirstPlay` 保持 false。
- 影响：引擎状态机、自对弈稳定性。写错会「上一墩的牌挡住下一墩」。
- 需用户拍板：否

**Q-033｜联机出牌阶段是否设回合计时**
- 来源：《开发文档》§14.5（可配置项）；《玩法说明》未提
- 问题：文档完全没提出牌超时/托管。联机时有人长时间不出牌会卡死整桌。
- 默认实现：**M3 先不设强制回合计时**（v1 无托管、无自动出牌），只在 UI 显示「等待 X 出牌」；文档 §14.5 保留配置位，后续版本可加「60s 自动 PASS / 领出时自动出最小单张」。
- 影响：M3 联机体验、服务端计时、断线重连。写错会导致联机局无法推进。
- 需用户拍板：是

**Q-034｜双地结束条件「在 L 走完之前」怎么判**
- 来源：《玩法说明》§6.3、§6.4；《开发文档》§7.5
- 问题：是靠「两个 F 的名次 ≤ 2」来判断，还是靠时间先后；若 L 和第二个 F 的走完在同一手（不可能）怎么算。
- 默认实现：用名次判定——`L.rank ∈ {1,2}` → L 赢并立即 SETTLE；`名次≤2 的 F 数 ≥ 2` → F 赢并立即 SETTLE；两者互斥不可同时成立；其他人不补名次、`rank` 保持 null。
- 影响：引擎 `isGameOver`、结算。写错会出现 2:1 被算成 2:0 或反过来。
- 需用户拍板：否

**Q-035｜PASS 计数的「一圈」口径**
- 来源：《玩法说明》§5.4、§5.5；《开发文档》§7.4
- 问题：玩家在「上一次出牌之前」PASS 过，之后又轮到他，是否还算「这一圈的 PASS」。
- 默认实现：PASS 计数全部在每次 PLAY 时清零；清零后按逆时针逐个玩家判「PASS 或出牌」，只有「自最后一次出牌以来连续的 PASS 数」达到其余在场人数才结束本墩。已 PASS 过的玩家在有人出牌后重新获得表态权（§5.5 过牌不锁定）。
- 影响：引擎墩结束判定、测试 F-01/F-02。写错会造成「提前结束墩」或「重复要求表态」。
- 需用户拍板：否

## 4. 供牌与回牌

**本节文档已明确、无需 DEFAULT**：供牌在下一局发完牌后执行（§7.1）；只影响紧接着的下一局、不累积（§7.1）；输家自动交最大牌、不能自选（§7.3）；♠3/♠A 永不出供/回（§7.3、§7.5、边界 #22/#23）；供出与回出的牌、供牌池、回牌池全部公开（§7.6）；每个输家「交几张收几张」、最终 4 人各 13 张（§7.5）。

**Q-036｜债务的生命周期与覆盖规则**
- 来源：《玩法说明》§7.1、§7.9、§6.5；《开发文档》§3.2、§8.1
- 问题：`pendingDebt` 何时生成、何时清空、多局之间如何覆盖。
- 默认实现：每局 SETTLE 时**重新生成**下一局债务（不累加）：平局 → `null`；明牌 → 本局债务已被作废且本局结果翻倍后重新生成；正常 → 按结算表生成。发牌/重发都不改债务；只有「平局」「明牌作废」「供牌执行完毕」三种情况会让它变 null。
- 影响：供牌状态机、结算、跨局一致性。写错会累积债务或丢债务。
- 需用户拍板：否

**Q-037｜供牌池分给赢家的顺序，以及「同分」情形**
- 来源：《玩法说明》§7.4；《开发文档》§8.4
- 问题：规则写「按得分高者优先；同分按出完名次靠前者优先」。但非双地赢家是 2 人，其得分只可能是 3+2 或 3+1（冠军队必含第 1 名），**同分实际不可达**；双地只有 1 个或 3 个赢家。
- 默认实现：仍按「得分降序、同分名次升序」实现并写单测（为 V2 累计分留口），但结算表保证不会走到同分分支；双地时 3 个赢家的得分是 {1,1,0}，锁定者排最后（见 Q-049）。
- 影响：供牌分配、测试。写错在双地 F 赢时分配顺序会乱。
- 需用户拍板：否

**Q-038｜赢家收到的张数不相等时，回牌怎么算**
- 来源：《玩法说明》§7.5；《开发文档》§8.4、§8.5
- 问题：规则只说「收到几张返还几张」，没说分配后张数不等怎么办。
- 默认实现：**当前结算表下必然整除**（非双地池 2 或 4 张、2 个赢家；双地池 6 或 12 张、1 或 3 个赢家）。为防未来改动，分配时用「剩余张数按顺序补 1」的规则：`base = floor(total/winnerCount)`，前 `total % winnerCount` 个赢家多拿 1 张；回牌义务严格等于各自实际收到张数。
- 影响：供牌/回牌、未来规则扩展。写错会出现「回牌池张数 ≠ 供牌总张数」。
- 需用户拍板：否

**Q-039｜回牌池张数与每个输家挑回张数**
- 来源：《玩法说明》§7.5、§9.7
- 问题：回牌池总张数、以及每个输家能挑几张，是否等于「他上交的张数」。
- 默认实现：回牌池 = 所有赢家返还牌之和 = 供牌总张数；每个输家挑回的张数 = 他本次上交的张数（交 2 挑 2、交 1 挑 1）；全部挑完后每人 13 张，并做守恒断言。
- 影响：供牌流程、手牌守恒测试。写错会让某人多/少一张，后续全乱。
- 需用户拍板：否

**Q-040｜回牌挑选顺序并列时怎么办**
- 来源：《玩法说明》§7.5；《开发文档》§8.5
- 问题：「按各自上交的最大牌从大到小」在 4~10 同点数时会并列（与 Q-011 同源）。
- 默认实现：与 Q-011 完全一致——按座位号升序（seat 0→3）决定先后，界面显示顺序与之一致；不使用 `cardId` 做 tie-break。
- 影响：回牌流程、测试确定性。写错会和首发权口径不一致，出现「同一并列在两处结果不同」。
- 需用户拍板：否

**Q-041｜赢家回牌超时后自动还什么牌**
- 来源：《开发文档》§8.5（超时自动返还手中最小的牌）；《玩法说明》未提
- 问题：超时默认值、以及「最小牌」是否要把 ♠3/♠A 排除。
- 默认实现：超时 10s；自动从**合法牌**（排除 ♠3、♠A）里按 `cmpCard` 取最小的若干张，数量 = 他实际收到的张数；同时广播 `RETURN` 事件标注 `auto: true`，UI 提示「超时自动返还」。
- 影响：UI/交互、供牌流程、公平性。若未排除地主牌，会产生非法回牌直接卡死流程。
- 需用户拍板：是

**Q-042｜输家挑回牌超时后自动挑哪张**
- 来源：《开发文档》§8.5（超时自动取最小）
- 问题：超时默认值、以及「从回牌池取最小」还是「取对他最有利的」。
- 默认实现：超时 10s；自动从回牌池按 `cmpCard` 取最小的一张，广播 `PICK_RETURN` 标注 `auto: true`。与「还最小牌」口径对称。
- 影响：UI/交互、供牌流程。写错会让输家超时后白捡大牌（不公平）。
- 需用户拍板：是

**Q-043｜供牌本身有没有超时**
- 来源：《玩法说明》§7.3（输家自动交最大牌）；《开发文档》§8.3
- 问题：供牌是系统自动完成，没有玩家输入，是否需要交互与超时。
- 默认实现：供牌（COLLECT）与分配（DISTRIBUTE）由服务端一次算完，无超时、无玩家输入；UI 只做「展示供牌结果」的过场（见 Q-099）。
- 影响：状态机、UI 流程。写错会多出无意义的等待态。
- 需用户拍板：否

**Q-044｜「供不出来」的判定条件**
- 来源：《玩法说明》§7.8、§9.9；《开发文档》§8.2
- 问题：判定条件到底是「可用牌数 < 需要张数」，还是「手牌张数 < 需要张数」；哪些局面会触发。
- 默认实现：`可用牌数（排除 ♠3/♠A）< amountPerLoser` 即触发。**唯一可达情形**：上一局双地明牌 L 输 → 欠 12 张 → 本局他又同时拿到 ♠3、♠A（双地），可用 11 张 < 12 张。其他所有组合（含 L 欠 6 张时持单张地主牌：可用 12 张 ≥ 6）都不触发。
- 影响：供牌 CHECK 分支、重发流程、测试。写错会把「供 6 张持 1 张地主牌」误判成供不出。
- 需用户拍板：否

**Q-045｜供牌取「最大 N 张」时，4~10 同点数怎么排**
- 来源：《玩法说明》§7.3 括号说明；《开发文档》§2.1 `cmpCard`
- 问题：规则说 4~10 同点数视为一样大、「谁先谁后不影响取最大的 N 张」；但实现要给出一个确定顺序。
- 默认实现：排序用 `cmpCard`（4~10 时以 `id` 稳定排序），保证结果集合确定、可回放；该排序**只影响展示顺序**，取出的牌集合与规则等价。涉及「谁的首发/谁先挑」的并列另按 Q-011/Q-040 处理。
- 影响：供牌排序、回放一致性。写错可能取错牌集合（例如把 4~10 当成不分花色后就随机挑）。
- 需用户拍板：否

**Q-046｜♠3/♠A 的硬校验放在哪一层**
- 来源：《玩法说明》§2.4、§7.3、§7.5；边界 #22/#23；《开发文档》§8.2、§8.5
- 问题：客户端可能提交含地主牌的回牌；另外地主牌绝不能通过任何方式转手，否则身份隐藏被破坏。
- 默认实现：服务端三重校验——(1) 供牌排序跳过这两张；(2) 回牌提交时校验，含 ♠3/♠A 直接非法动作；(3) 每局结束断言「♠3、♠A 的持有者没变」。客户端选择器直接禁用这两张。
- 影响：引擎供牌/回牌、隐藏信息、M3 防作弊。写错会让身份牌转手，整个身份玩法崩塌。
- 需用户拍板：否

**Q-047｜供牌后是否重算身份与锁定资格**
- 来源：《玩法说明》§2.4、§8.1；《开发文档》§7.3
- 问题：供牌换牌后，身份和锁定资格要不要重算。
- 默认实现：身份**永不重算**（地主牌不转手，身份在 DEAL 时定死）；锁定资格按**回牌结束后的手牌**重算（§8.1 明确「执行完供牌/回牌之后」），供牌前的判断作废。
- 影响：引擎锁定资格、UI 按钮。写错会出现「供牌前能锁、供牌后还亮着按钮」。
- 需用户拍板：否

**Q-048｜锁定者下一局是否照常参与供牌/回牌**
- 来源：《玩法说明》§7.2、§8.4；《开发文档》§3.2
- 问题：上一局提前锁定的人，在下一局已经拿到新牌、重新是普通玩家。他上一局算「输方」时要不要供牌。
- 默认实现：**照常**。锁定只影响本局名次与出牌，不影响下一局供牌义务；他若属于输方，则按结算表正常供牌（他手牌 13 张、可用张数足够），也正常参与回牌挑选。锁定的 13 张旧牌与本局无关。
- 影响：结算/供牌、边界测试。写错会让锁定者「白拿一局供牌豁免」。
- 需用户拍板：否

**Q-049｜双地 F 赢时，已锁定的那个 F 算不算「赢家」参与分供牌**
- 来源：《玩法说明》§6.4、§7.2、§7.4、§8.5；《开发文档》§10.2（`winnerSeats` 只取 `rank ≤ 2` 的 F）
- 问题：双地且 F 赢（两个 F 包揽 1、2 名）时，L 供 6/12 张。若本局还有第三名 F 提前锁定（rank 3、得 0 分），他属于赢得一方。开发文档 `computeResult` 的 `winnerSeats` 只列 rank≤2 的两个 F，导致这 6/12 张只在 2 个 F 之间分（各 3/6 张），锁定 F 一张不收也不用还。但规则 §7.2 的总张数（6/12）与 §7.4「赢家轮流拿」指向「3 个 F 都是赢家、各 2/4 张」。
- 默认实现：**按《玩法说明》**：胜方全部成员都是赢家。双地 F 赢时，3 个 F 都进入 `winnerSeats`（排序：得分 1 分的两人按名次、锁定者 0 分排最后），L 供的 6 张由 3 人轮流拿（各 2 张），明牌翻倍时各 4 张；回牌时 3 人各还 2/4 张，回牌池 6/12 张由 L 一人挑回 6/12 张。
- 影响：结算 `winnerSeats`、供牌分配、回牌、双地锁定局的经济性。写错会让锁定者少收牌、另两个 F 多收，明显影响平衡。
- 需用户拍板：是

**Q-050｜供牌/回牌的原子性与「临时超过 13 张」**
- 来源：《玩法说明》§7.5、§7.6；《开发文档》§8.4
- 问题：赢家收到供牌后手牌会临时变成 15 张（非双地大赢）或 25 张（双地翻倍 12 张），之后才回牌。这段中间态能否被玩家操作或看到。
- 默认实现：供牌 + 回牌视为**一个不可拆分的原子步骤**：期间 `legalActions` 全部返回空，禁止出牌/锁定/明牌等任何动作；UI 允许展示「供牌中」与手牌数变化（公开信息），但手牌内容只给本人。原子步骤结束后统一断言每人 13 张。
- 影响：引擎状态机、UI、服务端校验。写错会让玩家在 25 张时出牌。
- 需用户拍板：否

**Q-051｜CHECK 失败但当事人不是双地者（不变量破坏）的防御**
- 来源：《开发文档》§8.2
- 问题：按 Q-044 该情形不可达，但代码路径存在。若因 bug 走进来，给谁选项？
- 默认实现：抛引擎错误、记录 `ENGINE_INVARIANT_VIOLATION`，并降级为「跳过本局供牌、首发用 ♦4 持有者」，同时保留事件日志供复盘；正常对局不应触发，M1 自对弈 1000 局断言从未出现。
- 影响：错误处理、可观测性。写错会把 bug 悄悄吞掉，变成难查的规则偏差。
- 需用户拍板：否

**Q-052｜供牌/回牌是否公开「每张牌来自谁」**
- 来源：《玩法说明》§7.6、§7.5 示例、§7.7
- 问题：规则说供出的牌、回出的牌公开；但首发权依赖「上交最大牌的人」，玩家若看不到来源就无法理解首发，也会觉得不公平。
- 默认实现：公开到「牌 + 来源座位 + 顺序」：供牌池逐张标注是谁交的（`SUPPLY` 事件已含 `from`）；回牌池逐张标注是谁还的；输家挑回时也公开挑了哪张。§7.6「除此之外手牌不公开」不变。
- 影响：UI 展示、事件流、隐藏信息。写错会让首发看起来随机。
- 需用户拍板：否

## 5. 提前锁定

**本节文档已明确、无需 DEFAULT**：条件为「发完牌 + 执行完供牌/回牌后，13 张全为 4~10」（§8.1）；满足条件者必为 F（§8.1、边界 #34）；窗口 5 秒（§8.2、开发文档 §2.3 `LOCK_WINDOW_MS`）；只有 1 人选择则成功、2 人及以上全失败（§8.3）；成功者公开全部 13 张、固定第 3 名 1 分（§8.3、§8.4）；锁定者退出、不参与出牌、不被使用（§8.4）；非双地锁定后的三种结算（§8.5）；双地锁定后 L 拿 1/2 名即 L 赢、两个 F 包揽 1、2 名则 F 赢（§8.5）。

**Q-053｜锁定窗口 5 秒能不能提前结束**
- 来源：《玩法说明》§8.2；《开发文档》§9.2（「窗口 5s（可配置）」）
- 问题：固定等满 5s 还是可以提前结束；提前结束会不会泄露「有几个人符合条件/有人没表态」的信息。
- 默认实现：**允许提前结束**：当且仅当「所有符合锁定条件的玩家都已明确提交（锁定 / 不锁定）」时立即结束；否则等满 5s。不符合条件的人不参与表态，也不显示按钮。提前结束不改变保密性，因为其他玩家本来就不知道谁符合条件。
- 影响：UI/交互、状态机计时、热座体验（每局少等 5s）。写错要么每局白等 5s，要么提前结束泄露信息。
- 需用户拍板：是

**Q-054｜锁定资格判定时点与附加条件**
- 来源：《玩法说明》§8.1；《开发文档》§9.2（`hand.every(rank <= 10)`）
- 问题：除了「全部 ≤10」，是否还要求「手上正好 13 张」「没有 out」。
- 默认实现：判据三条同时成立——`hand.length === 13`、`every(rank <= 10)`、`!out`。判定时点为回牌结束、窗口开始；窗口内手牌不再变化，无需重算。
- 影响：引擎锁定资格、UI 按钮可见性。写错会让手牌不足 13 张的人也能锁。
- 需用户拍板：否

**Q-055｜2 人及以上锁定失败后，公开到什么程度**
- 来源：《玩法说明》§8.3；《开发文档》§9.2、§12 边界 #19
- 问题：规则说「选择过的人会收到『有人也想锁定』的提示，但不知道是谁」。要不要给人数、要不要给其他人提示。
- 默认实现：只给发起过 `LOCK` 的玩家各弹一条「本局锁定失败：有人也想锁定（不公开是谁）」，**不给人数、不给身份**；没发起过的玩家无感。失败者的手牌不公开，本局正常开打（他们也没有额外惩罚）。
- 影响：UI 提示、隐藏信息。写错会泄露「本局几个 F 手牌全低」这种强信息。
- 需用户拍板：否

**Q-056｜锁定窗口内能否反复切换「锁定 / 取消」**
- 来源：《玩法说明》§8.2、§8.3；《开发文档》§9.2（`intents` 在窗口结束时统计）
- 问题：点错了能不能取消；窗口结束时按什么算。
- 默认实现：窗口内**可以自由切换**（按钮是 toggle），服务端只保留每个座位的最新意向；窗口结束（含提前结束）时以最终状态为准，之后不可再改。
- 影响：UI/交互、服务端意向存储。写错要么「点错就锁死」，要么窗口结束后还能改。
- 需用户拍板：是

**Q-057｜锁定窗口内掉线 / 超时怎么办**
- 来源：《玩法说明》§8.2；《开发文档》§11.3（断线重连）
- 问题：断线玩家 5s 内没表态，算不算锁定。
- 默认实现：**视为「不锁定」**；重连后只能看到窗口结果，不能补选。服务端以窗口截止时刻的意向为准，不因掉线延长窗口、也不代打。
- 影响：UI/交互、断线重连、公平性。写错会让掉线玩家被代锁或被卡住。
- 需用户拍板：否

**Q-058｜锁定者占用第 3 名后，剩余名次怎么补**
- 来源：《玩法说明》§8.4；《开发文档》§10.1（`rankTaken[3]` + `nextFreeRank`）
- 问题：名次槽 1、2、3、4 里 3 被锁定者占住，剩下 3 个人怎么分 1、2、4。
- 默认实现：每局 `rankTaken[1..4]` 重置为 false；锁定成功时置 `rankTaken[3] = true`；之后按出完先后用 `nextFreeRank()` 从 1 往上找第一个空槽（跳过 3）。因此非双地时 L 的两人会拿到 2 和 4（合 2 分），双地时 L 可能拿到 4（0 分）——与 §8.5 的比分完全一致。
- 影响：引擎名次分配、结算、测试。写错会出现两个第 3 名或名次缺号。
- 需用户拍板：否

**Q-059｜非双地 + 锁定的三种结算能否直接当黄金用例**
- 来源：《玩法说明》§8.5、§9.11
- 问题：三种结局（F 剩 1 人拿第 1/2/4 名 → 4:2 小赢 / 3:3 平 / 1:5 大赢）是否要逐条写测试。
- 默认实现：直接作为 M1 的 3 条黄金用例（输入名次与锁定状态、输出比分与供牌），与《玩法说明》§8.5 数字逐字对齐；其中 3:3 是「锁定也可能平局」的唯一来源，不要漏。
- 影响：测试覆盖、结算正确性。写错会把平局算成小赢。
- 需用户拍板：否

**Q-060｜双地 + 锁定的胜负判定**
- 来源：《玩法说明》§8.5、§6.4
- 问题：双地时剩 L + 2F，锁定者占第 3 名，L 拿第 4 名（= 两个 F 包揽 1、2 名）算 F 赢；L 拿 1 或 2 名算 L 赢。名次只有一个 4 号位时怎么保证判定不歧义。
- 默认实现：沿用 Q-034 的判据——`L.rank ∈ {1,2}` → L 赢；名次≤2 的 F 数 = 2 → F 赢；锁定者不参与胜负判定；双地不补名次（未走完者 rank 保持 null）。
- 影响：引擎 `isGameOver`/`computeResult`、结算。写错会出现「L 明明第三走完却被判赢」。
- 需用户拍板：否

**Q-061｜锁定判定依据是「选择人数」还是「符合条件人数」**
- 来源：《玩法说明》§8.3
- 问题：如果 2 个人符合条件但只有 1 个人选择锁定，算成功还是失败。
- 默认实现：**只看选择锁定的人数**：恰好 1 人提交 `LOCK` → 成功；≥2 人提交 → 全部失败；0 人 → 无人锁定。符合条件者的数量、以及没点的人怎么想，都不影响。
- 影响：引擎锁定窗口逻辑、测试。写错会让「两个人符合、一个锁」被误判失败。
- 需用户拍板：否

**Q-062｜不符合条件的人提交锁定申请**
- 来源：《玩法说明》§8.1；《开发文档》§11.4（防作弊）
- 问题：客户端可能被改包提交 `LOCK`。
- 默认实现：服务端 `legalActions` 里没有 `LOCK` 就拒绝，返回「非法动作」并记录；不进入失败提示、不弹给任何人。UI 对不符合条件者不显示按钮。
- 影响：M3 防作弊、引擎合法性。写错会出现「地主方锁定成功」。
- 需用户拍板：否

**Q-063｜锁定者 13 张公开牌的生命周期**
- 来源：《玩法说明》§8.4、§7.6；《开发文档》§9.2（`publicCards`）
- 问题：公开的 13 张何时失效、下一局怎么清。
- 默认实现：锁定成功即广播 `LOCKED`（含 13 张牌），本局内一直公开在桌面；进入下一局 DEAL 时清空 `publicCards`（连同明牌公开的两张、已出牌记录里属于上一局的部分）；回放时按事件重建，不依赖快照。
- 影响：UI 展示、事件流、回放。写错会把上一局公开牌带到下一局，泄露信息。
- 需用户拍板：否

## 6. 结算

**本节文档已明确、无需 DEFAULT**：名次分 3/2/1/0（§6.1）；非双地 5:1 大赢、4:2 小赢、3:3 平局（§6.2）；双地 L 得 2 分、F 各得 1 分、先到 2 分、无平局（§6.3）；非双地一队两人出完立即结束、未出完者按剩余手牌数补 3/4 名（§6.4）；双地不补名次（§6.4、开发文档 §7.5 注）；平局不供牌不回牌、下一局 ♦4 首发（§6.5）。

**Q-064｜未出完者补名次时手牌数并列怎么办**
- 来源：《玩法说明》§6.4、§12 第 4 条；《开发文档》§10.2（按 `hand.length` 排序）
- 问题：两个未出完的人剩余手牌数相同，谁第 3、谁第 4。规则说「不影响队伍总分」，但个人的 `rank` 分（1 分 vs 0 分）需要唯一值。
- 默认实现：手牌数相同 → **按座位号升序（seat 0→3）取靠前者名次靠前**；并在 UI 上标注「按剩余张数补名次」。因为两人必属同一队，队伍总分与供牌张数不受影响（§6.4 已声明），仅显示与个人分不同。
- 影响：结算名次/显示、V2 累计分（若做累计分，这条会影响个人总分，需要在做 V2 时重新确认）。写错会影响个人分显示。
- 需用户拍板：否

**Q-065｜补名次的影响范围**
- 来源：《玩法说明》§6.4、§12 第 4 条
- 问题：补出来的 3/4 名会不会反过来影响胜负、供牌、「谁是赢家」。
- 默认实现：**只用于显示与个人名次分展示**：队伍总分与实际名次（第 1、2 名）不变；`winnerSeats/loserSeats` 仍按队伍判定；供牌张数只看大赢/小赢/明牌。实现上补名次在算完胜负后执行，且断言「补名次未改变 `lScore/fScore`」。
- 影响：结算、测试。写错可能出现「补完名次后比分变了」。
- 需用户拍板：否

**Q-066｜双地未走完者的显示口径**
- 来源：《玩法说明》§6.4；《开发文档》§10.2
- 问题：双地不补名次，未走完的人 `rank` 是 null，UI 显示什么。
- 默认实现：显示「未出完（-）」、得分 0，不显示第 3/4 名；结算面板里双地只列第 1 名、第 2 名（若存在）与锁定者，其余标「未完成」。
- 影响：UI 结算面板。写错会凭空造出双地 3/4 名。
- 需用户拍板：否

**Q-067｜平局判定**
- 来源：《玩法说明》§6.2、§6.5、§6.3
- 问题：平局是否只可能是非双地 3:3；有没有其他来源。
- 默认实现：平局 = 非双地且 `lScore === fScore`，只可能是 3:3（两队各 3 分）；双地永远不平局（2:0、2:1、0:2 三种）；带锁定的非双地也可能 3:3（§8.5 情形 2），同样算平局、不供牌、下一局 ♦4 首发。
- 影响：结算、供牌、首发。写错会出现「双地平局」或「锁定局不算平局」。
- 需用户拍板：否

**Q-068｜大赢/小赢的判定与张数**
- 来源：《玩法说明》§6.2、§7.2；《开发文档》§8.1
- 问题：用比分差还是名次模式判大/小赢；张数怎么换算。
- 默认实现：非双地用 `scoreDiff`：4 → 大赢，输方每人 2 张（共 4）；2 → 小赢，每人 1 张（共 2）；0 → 平局不供。双地不看比分差，只看是否明牌：未明牌总额 6（L 赢 → 3F 各 2；L 输 → L 供 6），明牌总额 12（3F 各 4 / L 供 12）。实现里补断言 `scoreDiff ∈ {0,2,4}`。
- 影响：结算 → 供牌映射、测试 S-01~S-08。写错会出现 5:1 只供 1 张这类偏差。
- 需用户拍板：否

**Q-069｜名次槽与 `nextRankSlot` 的重置时机**
- 来源：《开发文档》§3.2、§10.1
- 问题：`nextRankSlot` 单调递增，若不重置，下一局会从 5 开始。
- 默认实现：每局 DEAL（含 REDEAL 后重新开始本局）时重置 `nextRankSlot = 1`、`rankTaken[1..4] = false`、`finishOrder = []`；SETTLE 只读不写这些字段。
- 影响：引擎状态、多局连打。写错会出现第二局所有人名次为 null 或 5。
- 需用户拍板：否

**Q-070｜双地比分 2:0 / 2:1 / 0:2 怎么算**
- 来源：《玩法说明》§6.3、§6.4
- 问题：L 第 2 名走完时前面有 1 个 F，比分是 2:1；L 第 1 名时是 2:0。
- 默认实现：`lScore = L.rank ∈ {1,2} ? 2 : 0`；`fScore = 名次≤2 的 F 的人数`；不补名次、不因未走完的人加 1 分。UI 显示比分与结果（L 赢 / F 赢），并注明「双地不补名次」。
- 影响：结算、UI、测试 S-04~S-06。写错会把 2:1 显示成 2:0。
- 需用户拍板：否

**Q-071｜结算时的守恒/不变量校验**
- 来源：《开发文档》§13.5
- 问题：结算阶段除了比分，还要断言什么。
- 默认实现：每次 SETTLE 断言——(1) 供牌/回牌完成后 4 人各 13 张、总计 52 张；(2) ♠3、♠A 持有者在整局内未变；(3) 名次 1~4 不重复（双地允许 null）；(4) 比分落在结算表枚举内；(5) 债务张数 ∈ {0,2,4,6,12}。任一失败输出完整事件日志。
- 影响：自对弈 1000 局验收、回归测试。写错会带病进入 M2。
- 需用户拍板：否

**Q-072｜结算事件与结算面板要下发什么**
- 来源：《开发文档》§11.2（`SETTLE` 事件）
- 问题：`SETTLE` 事件字段文档只写了 `{ result, nextFirst }`，字段不够 UI 用。
- 默认实现：`SETTLE` 下发：名次表（含 null）、`lScore/fScore`、胜负方座位、供牌预告（谁供几张、是否明牌翻倍、总张数）、下一局首发座位与理由、本局是否平局。UI 结算面板必须能完整复述这些，方便玩家对账。
- 影响：事件流契约、UI 结算面板、回放。写错会导致 M2 结算页信息缺失、玩家不信任数字。
- 需用户拍板：否

**Q-073｜单局制还是累计分**
- 来源：《玩法说明》§12 第 3 条；《开发文档》§1、§14.5
- 问题：V1 到底做不做跨局累计分。
- 默认实现：**V1 只做单局独立结算**，不做累计分；`GameState` 里预留 `handNo`，但不存历史总分；结算面板只显示本局比分。抢风同样不做（V2）。
- 影响：数据模型、UI、服务端。写错会提前引入 V2 复杂度。
- 需用户拍板：否

## 7. 双地重发牌（REDEAL）

**本节文档已明确、无需 DEFAULT**：只有「双地明牌输 → 欠 12 张 → 下局又双地 → 最多只能供 11 张」这一种触发情形（§7.8、§9.9）；重发是「四人全部收回、重洗、重新各发 13 张」（§7.8）；重发后 12 张债务保留、发完再按同样规则判断（§7.8、§9.9）；程序保护上限 20 次、超出强制明牌（开发文档 §8.2、§14.2）。

**Q-074｜20 次上限的计数口径**
- 来源：《开发文档》§8.2（「同一局连续 REDEAL 超过 20 次」）、§14.2
- 问题：计数器在哪一层、什么时候清零、第 20 次还是第 21 次触发。
- 默认实现：`GameState.redealCount` 每局（`handNo`）独立计数、每局 DEAL 时清零；每次成功执行 `REDEAL` 加 1；当 `redealCount >= 20` 时**不再允许 REDEAL**，只剩「明牌」选项（第 21 次重发不会发生）。计数与「连续」无关，只看本局累计次数。
- 影响：状态机、重发分支、测试（构造性测试可把上限调成 2 来覆盖）。写错可能死循环。
- 需用户拍板：是

**Q-075｜强制明牌的具体行为**
- 来源：《玩法说明》§7.8、§2.5；《开发文档》§8.2、§14.2
- 问题：超上限被强制明牌时，是否等同自愿明牌（公开 ♠3/♠A、作废债务、他首发、本局结果翻倍）。
- 默认实现：**完全等同自愿明牌**：公开 ♠3/♠A、`pendingDebt = null`、由他首发、本局结果按明牌翻倍生成下一局债务；额外广播 `REVEALED { forced: true }` 与 UI 提示「已达重发上限，强制明牌」。因为明牌必为 L，且明牌后本局若输又会产生 12 张债务，可能出现债务反复（见 Q-006）。
- 影响：状态机、结算、供牌、平衡性。写错会让玩家「强制明牌却不用翻倍」，规则不自洽。
- 需用户拍板：是

**Q-076｜重发后债务是否变化**
- 来源：《玩法说明》§7.8、§9.9；《开发文档》§8.2
- 问题：重发会不会让债务张数/翻倍状态变化。
- 默认实现：**不变**。`pendingDebt` 的张数、`mode`、`amountPerLoser`、`revealed` 标志原样保留；重发既不消耗也不增加债务；重发也不改变「上一局是否明牌」这个事实。
- 影响：供牌、状态机。写错会出现「重发一次债务翻倍」的雪球。
- 需用户拍板：否

**Q-077｜重发后的状态重置清单**
- 来源：《玩法说明》§7.8；《开发文档》§7.1、§7.3
- 问题：重发要重置哪些字段，`handNo` 会不会 +1。
- 默认实现：回收 52 张 → 重洗 → 各发 13 张；清空本局 `publicCards`、明牌记录 `revealedSeat`、锁定意向、`passesSinceLastPlay/topPattern/topSeat/threePhase/isFirstPlay`；重算 `doubleSeat`、`landlordSeats`；`handNo` 不变；`redealCount` 保留；phase 回 `DEAL`。
- 影响：状态机、UI、回放。写错会带着上一副牌的公开信息进新局。
- 需用户拍板：否

**Q-078｜重发后供牌 CHECK 是否重跑**
- 来源：《玩法说明》§7.8（「发完之后再按同样规则判断」）
- 问题：重发后是否重新判断「供不出来」。
- 默认实现：**重跑**。重发后回到 REVEAL → 若 CHECK 仍失败（新牌又是双地）→ 再给「明牌 / 重新发牌」选项，直到成功或触达上限；若新牌不再双地 → 正常执行供牌（债务保留）。
- 影响：供牌流程、状态机。写错会出现「重发后债务被跳过」或「同一副牌反复判断」。
- 需用户拍板：否

**Q-079｜重发后是否重新询问明牌**
- 来源：《玩法说明》§7.8、§2.5；《开发文档》§7.1
- 问题：重发后身份变了，明牌机会要不要重新给。
- 默认实现：**重新询问**。重发等同于「新的发牌」，REVEAL 阶段按新身份重新走（可能换人双地）；上一轮的明牌意向与「是否已拒绝明牌」全部清空。
- 影响：REVEAL 阶段、UI 弹窗。写错会出现「重发后双地者永远没机会明牌」。
- 需用户拍板：否

**Q-080｜重发的公开范围**
- 来源：《玩法说明》§7.6、§7.8
- 问题：重发时其他三家怎么知道发生了什么、要不要公开债务细节。
- 默认实现：广播 `REDEAL { seat, reason: 'SUPPLY_IMPOSSIBLE', attempt }`，并公开「该玩家本局需供 N 张、只能供 11 张」这层事实（供牌张数本来就在上一局结算时公开）；不公开他的新手牌。UI 提示「重新发牌（原因：供牌不足）」。累计次数也公开（避免玩家怀疑作弊）。
- 影响：UI、隐藏信息、公平性。写错会让重发显得可疑。
- 需用户拍板：否

**Q-081｜重发的唯一触发源与可回放性**
- 来源：《玩法说明》§7.8；《开发文档》§13.5、§11.3
- 问题：还有没有别的重发理由（如发牌异常）？随机数怎么保证可复现。
- 默认实现：**只有 Q-044 那一种触发源**，任何其它情况不得重发；洗牌使用注入的 seeded RNG，REDEAL 事件记录 `seed`/`redealCount`/重发前手牌快照（仅日志，不进客户端），保证「同种子 + 同动作序列 → 同结果」的回归测试可复现。
- 影响：测试可复现性、回放。写错会让 1000 局自对弈无法定位失败原因。
- 需用户拍板：否

**Q-082｜重发期间其他玩家的等待**
- 来源：《玩法说明》§7.8；《开发文档》§7.2
- 问题：重发由一个人的选择触发，另外三人要不要有操作、会不会被卡住。
- 默认实现：其他三人无操作、只看到「重新发牌中」；重发是同步原子步骤（服务端一次完成），不设超时；若触发者掉线，则按其「重发选择超时」默认动作处理（见 Q-096）。
- 影响：UI、断线重连。写错会让重发期间卡住整桌。
- 需用户拍板：否

**Q-083｜`canPlayTripleLike` 里「结束牌只在 `isLeading` 时判断」是否与规则冲突**
- 来源：《玩法说明》§3.5 第 3 条、§5.7.6；《开发文档》§5.4
- 问题：开发文档把结束牌限定在 `isLeading`，规则写「轮到他领出时」。
- 默认实现：**结论：不冲突，开发文档是对的**。补充两点实现要求：(1) 三条阶段内以结束牌领出时，仍必须压过基准牌；(2) 加断言「非领出状态下，`hand.length === p.cards.length` 不得作为可出依据」。另把「本局第一手」条件补成「由首发座位打出」（C-04）。
- 影响：引擎合法性判定、测试 F-08/F-09。写错会让「跟牌时用最后 3 张三条走完」成为合法动作。
- 需用户拍板：否

**Q-084｜`buildDebt` 的 `amountPerLoser = total / losers.length` 是否正确**
- 来源：《开发文档》§8.1；《玩法说明》§7.2、§7.8
- 问题：3 个 F 时 6/3 = 2、12/3 = 4；L 输时 6/1 = 6、12/1 = 12，是否有整除风险。
- 默认实现：**当前结算表下全部整除，数值正确**（非双地不走这个分支）。但要补三项防御：(1) 生成时断言 `total % losers.length === 0`；(2) 输家列表必须来自本局结算的 `loserSeats`（双地 L 赢时为全部 3 个 F，含锁定者，见 C-03）；(3) 明牌作废后 `pendingDebt` 已是 null，SETTLE 只能重新生成、不能复用旧对象。
- 影响：结算 → 供牌映射、测试 S-04~S-08。写错会出现小数张数或除零。
- 需用户拍板：否

**Q-085｜`onPass` 的 `passesSinceLastPlay >= activeSeatCount - 1` 在顺风/锁定后是否成立**
- 来源：《开发文档》§7.4；《玩法说明》§5.4、§5.6、§8.4
- 问题：门限依赖「在场人数」与「topSeat 一定在场」，锁定者和出完者会减少在场人数，顺风会换 topSeat。
- 默认实现：**在三个前提下成立**：(1) `activeSeatCount` 用 `!out` 计数（锁定者 `out=true` 天然排除，Q-020）；(2) 领出不可 PASS（Q-022）；(3) 顺风分支必须 `passesSinceLastPlay = 0` 并更新 `topSeat/topPattern`（Q-024、Q-031）。满足后建议仍改成显式的 `otherActiveCount()`，不用减法，防止后续改规则时算错。
- 影响：引擎墩结束判定、自对弈死锁率。写错会死锁或提前结束。
- 需用户拍板：否

**Q-086｜`isGameOver` 的双地判定与规则是否一致**
- 来源：《开发文档》§7.5；《玩法说明》§6.3、§6.4
- 问题：用 `rank <= 2` 判定「L 走完」「两个 F 走完」，是否会出现名次槽被锁定占用后的误判。
- 默认实现：**判据一致**：`L.rank ∈ {1,2}` 或「名次≤2 的 F 数 ≥ 2」即结束；锁定者固定 rank 3 不参与；未走完者不补名次。补两条断言：(1) 结束瞬间两条件不得同时为真；(2) 双地局中 `rank === 3` 只可能是锁定者。
- 影响：引擎结束判定、结算。写错会出现「L 第三走完却判 L 赢」。
- 需用户拍板：否

**Q-087｜明牌后 `pendingDebt = null` 与「本局翻倍」是否矛盾**
- 来源：《开发文档》§9.1；《玩法说明》§2.5
- 问题：一边把债务清空，一边结算时读 `revealedSeat` 翻倍。
- 默认实现：**不矛盾，是规则要求的两个独立效果**：清空 = 上一局债务作废（本局不供不回）；翻倍 = 本局结果生成下一局债务时按 12 张计。实现要求：(1) `revealedSeat` 在每局 DEAL 重置为 null，避免用下一局的标志去翻上一局的倍；(2) 注释写明「作废的是整局全部供牌/回牌」，见 C-11；(3) SETTLE 生成债务时以「本局 `revealedSeat`」为唯一依据。
- 影响：供牌、结算、跨局边界。写错会出现「明牌后债务既作废又照扣」或「翻倍算到错误的一局」。
- 需用户拍板：否

**Q-088｜`firstSeatBySupply` 的字段归属不一致（实现风险）**
- 来源：《开发文档》§3.2（`GameState` 无此字段）、§3.3（在 `SupplyContext` 里）、§8.6（`resolveFirstSeat` 读 `state.firstSeatBySupply`）
- 问题：三处写法不统一，照抄会编译不过或读到 undefined。
- 默认实现：统一为 `state.firstSeatBySupply: number | null`，在 `SupplyContext` 完成后写回 `GameState`，`SupplyContext` 只保留过程数据；`resolveFirstSeat` 只读 `GameState`。
- 影响：引擎代码结构、类型检查。写错会出现「首发永远回退到 ♦4」。
- 需用户拍板：否

**Q-089｜回牌超时「还最小牌」遗漏地主牌（文档缺口）**
- 来源：《开发文档》§8.5 注释；《玩法说明》§7.5、边界 #22
- 问题：注释写「超时则自动返还手中最小的牌」，但 ♠3/♠A 不能作为回牌；若手里最小的是 ♦4 之外的…尤其地主牌恰好是「最小的合法牌」时（例如手里只有 ♠3 与若干大牌），自动逻辑会选出非法牌。
- 默认实现：自动回牌 = 合法牌集合（排除 ♠3/♠A）中按 `cmpCard` 最小的若干张；若合法牌不足（理论上不可能，见 Q-044），走 Q-051 的降级路径。
- 影响：供牌流程、UI 超时逻辑。写错会在超时后产生非法回牌、卡死供牌阶段。
- 需用户拍板：否

**Q-090｜状态模型缺重发字段（文档缺口）**
- 来源：《开发文档》§3.2、§8.2、§14.2
- 问题：`Phase` 里没有 REDEAL，`GameState` 里没有 `redealCount`，但 §8.2 要求「同一局连续 REDEAL 超过 20 次」。
- 默认实现：`GameState` 增加 `redealCount: number`、`redealReason: 'SUPPLY_IMPOSSIBLE' | null`；`Phase` 不新增 REDEAL（用 DEAL 循环表示，见 §7.1 流程图），但事件层加 `REDEAL`；M1 测试用一个可配置的 `maxRedeal`（默认 20）来快速覆盖上限分支。
- 影响：状态机、测试。写错会导致上限逻辑无处安放。
- 需用户拍板：否

**Q-091｜逐条核对后确认「无需改动」的部分**
- 来源：《开发文档》§12、§13；《玩法说明》§10
- 问题：避免误改已正确的内容。
- 默认实现：以下已逐条核对，**与《玩法说明》一致、不要动**：
  - 边界 #1~#21（等值可压、花色比较、顺子/同花/同花顺比较方向、炸弹不能压单张对子、三条夹一 vs 顺子档位、过牌后可再出、供牌跳过 ♠3/♠A、回牌拒绝地主牌）；
  - 测试 C-01~C-13、T-01~T-13、F-01~F-09 全部与规则一致（含 F-08/F-09 结束牌）；
  - §8.4 分配示例（C 拿 ♥3、D 拿 ♣3、C 拿 ♠2、D 拿 ♦2）与 §7.4 示例一致；
  - §10.3 结算表与 §6.2/§6.3/§7.2 一致；
  - §9.8 数字自洽：明牌 L 赢 → 3F 各 4 张共 12，收牌者手牌临时 25 张、返还 12 张后 13 张。
- 影响：避免在修 C-01/C-02/C-03 时误伤正确逻辑。
- 需用户拍板：否

## 9. UI / 交互口径

**本节文档已明确、无需 DEFAULT**：供牌、回牌、明牌公开的牌、锁定公开的 13 张、已出的牌全部公开（§7.6、§2.5、§8.4）；其余手牌不公开（§7.6）；明牌与锁定都在出牌前完成（§5.1）；客户端只做合法性提示、最终判定在服务端（开发文档 §11.1）。

**Q-092｜明牌倒计时的 UI 表现**
- 来源：《开发文档》§7.2（10s、默认不明牌）；《玩法说明》§2.5
- 问题：倒计时怎么显示、最后几秒要不要提醒、超时后怎么告知。
- 默认实现：双地者看到居中弹窗「你是双地（♠3 + ♠A）：可明牌取消本局供牌并首发，本局供牌翻倍」+ 10s 环形倒计时；最后 3s 变红；超时自动关闭并 toast「未明牌」。其他玩家只看到「等待 X 决定是否明牌」，不显示其身份（明牌前不公开）。
- 影响：UI、玩家预期。写错会让其他人提前知道谁是双地。
- 需用户拍板：否

**Q-093｜锁定窗口的 UI 表现**
- 来源：《玩法说明》§8.2、§8.3；《开发文档》§9.2
- 问题：窗口怎么展示、谁能看到按钮、提前结束怎么表现。
- 默认实现：全局显示 5s 倒计时；符合条件者看到 toggle 按钮「提前锁定第三名（仅自己可见）」，点后变为「已选择锁定（点击取消）」；不符合条件者只看倒计时。所有符合条件者提交后窗口立即结束（需用户拍板见 Q-053）。结果公布时：成功 → 亮出锁定的 13 张牌 + 「X 锁定第 3 名」；失败 → 只给申请者 toast。
- 影响：UI、状态机计时、保密性。写错会泄露资格信息或每局空等 5s。
- 需用户拍板：否

**Q-094｜赢家回牌选择器的口径**
- 来源：《开发文档》§8.5；《玩法说明》§7.5
- 问题：还牌时默认选中什么、张数怎么限制、超时怎么提示。
- 默认实现：弹出「请返还 N 张」选择器，默认预选**合法牌中按 `cmpCard` 最小的 N 张**（排除 ♠3/♠A，卡片置灰不可选），必须正好 N 张才能提交，10s 倒计时；超时提交默认选中的牌并 toast「超时自动返还最小牌」。
- 影响：UI、供牌流程。写错会导致回牌数量不符或选中地主牌。
- 需用户拍板：否

**Q-095｜输家挑回牌的 UI**
- 来源：《玩法说明》§7.5、§7.6；《开发文档》§8.5
- 问题：回牌池怎么展示、要不要显示来源、挑几张、超时怎么算。
- 默认实现：显示回牌池（按大小降序，每张标注「来自 X」），输家按 Q-040 的顺序依次挑，每人挑自己上交的张数；轮到谁就高亮谁，10s 倒计时，超时从池中取最小一张（Q-042）并 toast。挑完的牌进入其手牌。
- 影响：UI、供牌流程、公平性。写错会让挑牌顺序与首发口径不一致。
- 需用户拍板：否

**Q-096｜双地重发牌选择的超时默认**
- 来源：《开发文档》§8.2（只写了「给两个选项」）；《玩法说明》§7.8
- 问题：这个二选一弹窗的超时时间与默认动作文档没写。
- 默认实现：10s；超时自动选「**重新发牌**」（债务保留，不额外产生翻倍债务），并计入 Q-074 的 20 次上限；触达上限后弹窗只剩「明牌」，不再超时。UI 提示「超时已选择重新发牌」。
- 影响：供牌/重发流程、平衡性。写错会让超时被强制明牌，凭空产生 12 张债务。
- 需用户拍板：是

**Q-097｜断线重连在各决策阶段的兜底动作**
- 来源：《开发文档》§11.3；本文 Q-001/Q-057/Q-082/Q-096
- 问题：玩家在明牌、锁定、回牌、挑回牌、重发选择中断线时，服务端怎么继续。
- 默认实现：计时照走，超时按各条默认动作落子——明牌 → 不明牌；锁定 → 不锁定；回牌 → 还最小合法牌；挑回牌 → 取池中最小；重发选择 → 重新发牌；重连后只下发给本人「结果 + 我的新手牌」，不重放中间过程。断线 30s 内可重连（M3 验收要求）。
- 影响：M3 联机、服务端权威、玩家体验。写错会导致一桌人卡死。
- 需用户拍板：是

**Q-098｜隐藏信息的展示口径：是否公开各家剩余手牌张数**
- 来源：《玩法说明》§7.6；《开发文档》§11.1、§11.4
- 问题：规则只说「手牌不公开」，没说「张数」是否公开。但顺风、补名次、结束判定都需要张数，玩家也普遍会数牌。
- 默认实现：**公开剩余张数、不公开内容**：每家显示「X 张」（明牌/锁定者直接显示牌面）；供牌池、回牌池、已出的牌全部公开。客户端内存中不得出现别家手牌内容（M3 验收会抓包检查）。
- 影响：UI、隐藏信息、M3 防作弊验收。写错要么玩家无从判断局势，要么泄露手牌。
- 需用户拍板：是

**Q-099｜供牌/回牌的演出节奏**
- 来源：《玩法说明》§7.4、§7.5；《开发文档》§8.4
- 问题：供牌是自动的，UI 要不要停、停多久。
- 默认实现：分两屏展示，各停 1.5s 或等玩家点「继续」（热座必须点击、联机可自动推进）：第一屏「供牌：A 交 ♥3、♣3；B 交 …，共 N 张」；第二屏「分配/回牌：…」。全程无玩家输入，只是展示公开信息。
- 影响：UI、节奏。写错会让流程太快看不清或太拖沓。
- 需用户拍板：否

**Q-100｜移动端竖屏的关键操作路径**
- 来源：《开发文档》§1（Web 版）；START-HERE M2 验收（手机竖屏基本可用）
- 问题：文档没给具体布局与操作约束。
- 默认实现：单列布局——顶部三家（身份/张数/是否锁定），中间牌桌区（最近一手、供牌池、回牌池），底部自己的手牌（横向滚动、多选高亮），最底固定操作条（出牌 / 不要 / 明牌 / 锁定），触控目标 ≥ 44px；出牌选择支持点选 toggle，非法组合时「出牌」置灰。
- 影响：M2 验收、可用性。写错会在手机上点不到。
- 需用户拍板：否

**Q-101｜结算面板必显信息**
- 来源：《玩法说明》§6、§7.2、§7.7；《开发文档》§11.2
- 问题：结算面板要显示到什么程度，玩家才能对账。
- 默认实现：必显——四家名次与分数（双地未走完者标「未完成」）、两队总分、胜负结论（大赢/小赢/平局/L 赢/F 赢）、下一局供牌预告（谁供几张、是否明牌翻倍、合计几张）、下一局首发与理由（明牌者/供最大牌者/♦4）。可折叠显示本局已公开牌与事件流水。
- 影响：UI、玩家信任、M2 验收。写错会出现「结算数字看不懂」。
- 需用户拍板：否
